# Caveman FX: native hook + companion trainer (Trevor's stream branch)

Decided by Trevor, 2026-10-21: state effects (riding, grinding, manuals, **specific tricks**) on decks and wheels, for a stream gimmick ("maximum cool factor"). A personal branch for now; **stock Caveman decks must be unaffected**. Caveman owns its mod: native code, hooks and memory reads are fine (memory: caveman-own-the-mod); the goal is to survive game and ReSkate updates.

## Why native

Item data alone cannot do it (knowledge/state-effects-runtime.md): the game builds a deck's or wheel's effects on the **board's** effects record, whose animation context has none of the skater's states (the live probe: riding reads 1 on the skater's record, Default 0 on the board's), and an item in the shared bundle cannot even import the root-level states (grind, manual, the trick enums). Only skater items (costumes) land on the skater's record.

## Design

- **Our own trigger states.** FX decks and wheels trigger (TriggerType 6) on `BoolAsset`s Caveman ships in the shared bundle (`animation/caveman/fx.<name>`). They are reachable (no crash: statecheck-clean) and give non-null views; on their own they read `Default` (False), so without the DLL the decks simply show nothing extra.
- **The DLL answers for them.** `caveman_fx.dll`, loaded into Skate.exe, replaces slot 3 of the `BoolAsset` bool-view vtable (`exe+0x61ab080`, the getter `0x11dd4c0(view, ctx)` that the trigger update calls). For a view whose asset (view - 0x60) is one of ours it returns the DLL's value; for every other asset it calls the original. Context no longer matters.
- **Rules.** The DLL reads the skater's real states in the skater's context: root-level `BoolAsset`s (grinding, manual, in air, landing, bails) and the trick enums (`enumgs.anim.currentfliptrick`: Kickflip 2, Heelflip 3, ...; `enum.gs.anim.currentgrindtype`), found at run time. Rules map them to our fx states (kickflip -> `fx.kickflip`, grinding -> `fx.grind`, ...), with hold times and cooldowns.
- **Companion trainer.** A separate program (CLI first, then a panel in the Caveman app) talking to the DLL over a named pipe: live skater state, fire an fx state by hand or by hotkey, edit the rules, presets for stream.
- **Robust to updates.** Check the exe's SHA-256; find code and tables at run time by byte patterns and the game's own data (names, GUIDs); validate every pointer; on any mismatch stay dormant (never crash the game). ReSkate hooks `build_effects` and `register_skater`; we hook neither (a vtable slot, not a code patch).
- **Loading.** Injected after ReSkate attaches (the trainer or Caveman.exe: `CreateRemoteThread` + `LoadLibraryW`), or a proxy DLL later.

## Where it goes next (Trevor, 2026-10-21)

**Custom effects are the priority.** Beyond turning game effects on and off: drawing things *around* the skater in the style of NFS Unbound's cartoon overlays (speed lines, arrows, smoke puffs, stylised marks on the wheels), reacting to tricks. Two routes, not exclusive:

- **Game effects with our own art**: effect blueprints (emitters, ribbons, sprites) carrying Caveman's own textures, shipped as data and fired by the DLL through fx states. Uses the game's renderer, lighting and depth for free.
- **The DLL draws**: hook the D3D12 swapchain's Present (the technique ReShade, OBS game capture and overlay tools use) and draw world-space sprites and lines at the board's and wheels' positions (needs the camera matrices and the board's transform from game memory). Full control over the look; the same D3D12 hooking also gives streaming video onto a deck (decode each frame and copy it into the deck's texture), the fallback if the engine's own movie textures (`MovieTexture2Asset`) cannot be put on a deck by data alone. **Decided 2026-10-21 (Trevor): video decks go through the DLL.** The data-only route exists only through a UI render target that level data must spawn (six level bundles patched, every video decoding all the time; knowledge/movie-textures.md), so it is parked.

**Live equip control and our own cosmetics UI** (Trevor, 2026-10-21; after the effects). The game's cosmetics browser is painful; ReSkate already adds favorites, search and filters to it through its console (`items fav`, `items search <text>`, `items filter all|favorites|mods|game`; `Extension/Customization/item_browser.cpp`, favorites in `ReSkate.favorites.json` beside Skate.exe). The bigger idea: the DLL exposes "equip item X in slot Y" (an outfit is a set of recipes, slot -> item key, saved in the ReSkate profile's `cosmetic_loadouts`; ReSkate's multiplayer already has the game build a skater from a recipe at run time), and the trainer / Caveman app becomes the cosmetics UI: folders, tabs, favorites, search, thumbnails, presets; stream features (randomise the outfit every N seconds, chat picks the deck, a deck per trick). Needs: the function the customization menu calls to equip (reverse engineering, read-only first). An in-game overlay menu is possible later through the same D3D12 hook as the "DLL draws" effects.

  - **The jitter, explained** (read only, `caveman-trainer probe-timing`, 13:20, Trevor riding): the game simulates at a fixed 60 Hz (the "Simulation rate" setting: 30 or 60) and presented 88 frames a second. The board entity's transform and the camera object both change exactly 60 times a second, at different moments (never within 0.7 ms of each other), so a read at Present mixes ticks, and each frame is drawn from interpolated transforms anyway: the bars wobble against the board in motion, and the uneven 60-in-88 cadence reads as doubled ends. The renderer's own **transform proxies** (vtable exe+0x65eff48: +0x48 the render object, +0x50 this frame's world matrix, +0x90 the previous frame's) change exactly once per present, at the same moment, for the board (its render object a skinned mesh of 16 bones) and for the renderables that sit on the camera. **The bars now take the camera and the board from those** (`bars set timing frame`, the default; `tick` is the old way): the worker finds them by a scan for the proxy vtable and picks them against the simulation's pair (`src/proxy.rs`); the render thread reads both every frame, checks them against the simulation's (within 1.5 m; the board's must move when the board moves), and on any doubt falls back to the simulation's pair and asks for a new search.
  - **Occlusion against the game's depth** (`draw depth on|off`, on by default; `src/depth.rs`): three more vtable slots, on D3D12Core's command list class (`ResourceBarrier`, `RSSetViewports`, and `Barrier` for enhanced barriers, only counted). A transition out of DEPTH_WRITE ends a depth pass; the main view's depth is the largest single-sample 2D depth target with the back buffer's aspect. The depth is **not** read at Present (Frostbite may have reused its memory by then, and its state there is only known by replaying every list): right after the game's own barrier takes it out of DEPTH_WRITE, in the same command list, on the game's thread, the hook records the depth plane from the state the game just gave it to COPY_SOURCE, a copy into a texture of ours, and back. The depth is left exactly as the game expects. The copy in the newest list submitted is the one the overlay reads; the viewport the thread set last gives the part the frame used (upscalers render smaller). The scale (near plane, reversed or not) is calibrated on the deck: three points of it are read back each frame where the view depth is known (reversed depth stores about n / z, standard about 1 - n / z); the median of the last 300 gives n once they agree within 6 %. A bar pixel is hidden where the scene is more than `depth_bias` (3 cm) nearer the camera. `draw depth near M` sets the near plane by hand.

## The DLL draws (built 2026-10-21: the overlay and the bars)

The route for custom effects that are not the game's own (NFS Unbound-style cartoon overlays: speed lines, arrows, smoke puffs, marks on the wheels), and for video on a deck. The first effect, the equaliser bars, is built: `crates/caveman-fx/src/overlay.rs` (hooks and drawing), `scene.rs` (camera and board), `bars.rs` (settings, levels, geometry), `proxy.rs` (the frame's transforms), `depth.rs` (the game's depth), `audio.rs` (WASAPI bands), `rtti.rs`, `vhook.rs`.

- **How ReSkate draws** (its source, `Extension/UI/Overlay/overlay.cpp`, `overlay_render.cpp`): ImGui with its DX12 backend, from MinHook-style code detours on `CreateDXGIFactory1` (sl.interposer's, else dxgi's), the factory's `CreateSwapChain` and `CreateSwapChainForHwnd`, and the swap chain's `Present` (8), `ResizeBuffers` (13), `Present1` (22), `ResizeBuffers1` (39); for Streamline's wrapper it detours the wrapped DXGI swap chain's functions too. It binds each swap chain to the queue it was made with (`DingoSDKOverlayBindDx12`), draws in the outermost Present (a thread-local guard) on that queue, and holds the back buffers between frames (released in its resize detour). In the game (ReSkate.log): the swap chain is Streamline's wrapper over DXGI's; HDR10 output (buffer format 24 on an HDR display).
- **How we chain**: no code is patched. The vtable slots of DXGI's swap chain (`Present`, `Present1`) hold our hooks and call what they held, which is DXGI's function, entered through ReSkate's and Steam's detours. The game calls Streamline's wrapper; ReSkate's detour on it draws ImGui; Streamline calls DXGI's Present through the vtable: our hook draws the bars, then DXGI's (detoured) function runs. Both draw; the bars land over ReSkate's menus. Hooking the wrapper's slots as well (`draw streamline on`) draws first, under ReSkate's menus, but ReSkate's hook setup for a later swap chain compares the wrapper's slot with the function it detoured and would fail on ours, hence off by default. ReSkate may detour our own Present if the game makes a new swap chain while we are loaded (it reads DXGI's slot then): unload notices our code changed and keeps the DLL loaded (inert, the slots back), never pulling code out from under a detour. Our dummy swap chain may itself come back as Streamline's wrapper (seen 2026-10-21 13:05: its vtable was sl.interposer's); install then asks it for the swap chain it wraps and hooks DXGI's (when that vtable is in dxgi.dll).
- **The queue**: `GetDevice(ID3D12CommandQueue)` on a D3D12 swap chain answers E_NOINTERFACE (seen in the host test), so the queue comes from the DXGI swap chain object: it holds the queue it presents with at +0x140 (the game's, live read only: a D3D12Core `VCGraphicsCommandQueue` of the game's Agility SDK `x64\D3D12Core.dll`, also held by Frostbite's `CD3D12Renderer` and Streamline's `SwapChainData`; the same +0x140 in the host). A pointer is taken only when its vtable is the real queue's (learnt from our dummy queue), then checked: DIRECT, the back buffer's device. Fallbacks: the busiest DIRECT queue seen in `ExecuteCommandLists`. Streamline's wrapper gives the DXGI swap chain it wraps through its base interface (`StreamlineRetrieveBaseInterface`, the GUID ReSkate uses); every swap chain is asked for it first, whatever vtable was hooked (when the hook sat on the wrapper on 2026-10-21, the scan looked in the wrapper and fell back to the busiest queue).
- **Drawing**: in Present, before calling through: the back buffer (`GetBuffer`, released after the frame), our allocator of the ring once its fence passed (at most 2 ms wait, else the frame is skipped), the vertices (64 bytes each, already in clip space: the CPU projects with the camera's world matrix and vertical FOV and the back buffer's aspect, as ReSkate's nametags do) into the slot's upload buffer, PRESENT to RENDER_TARGET, one draw, back to PRESENT, executed on the game's queue, our fence signalled. Premultiplied-alpha blending (source ONE, destination INV_SRC_ALPHA): the solid style writes (colour x coverage, coverage) and replaces the picture under it, exactly in every output encoding; the glow style and the test rectangle write (colour x coverage, 0) and add. The pixel shader's 12 root constants: the output mode and brightness, the depth test's switch and bias, the depth texel mapping, the depth scale; one SRV (the depth copy, or a null SRV) from our own shader-visible heap (two banks, one per copy generation).
- **The frame's transforms** (`src/proxy.rs`, the jitter fix): the camera object and the board entity (below) change once per simulation tick, at different moments, while frames are drawn from interpolated transforms; the renderer's transform proxies (vtable exe+0x65eff48: +0x48 the render object, +0x50 this frame's world matrix in rows, +0x90 the previous frame's; about 12,000) change once per frame, together. The worker scans for the proxy vtable (resident private memory, in steps, while the bars are on) and picks the proxy nearest the simulation's board whose rows agree and whose render object is a skinned mesh (exe+0x65f2910, 1 to 64 bones; the deck has 16) and the proxy on the simulation's camera with the camera's rows. Every frame the render thread reads both (twice, until two reads agree), uses them when they are within 1.5 m of the simulation's and the board's keeps moving with the board, else falls back to the simulation's pair and asks for a new search. The field of view stays the camera object's.
- **Depth** (`src/depth.rs`): hooks in D3D12Core's command list tables: `ResourceBarrier` (26), `RSSetViewports` (21), `Barrier` (80, enhanced barriers: counted, not used). Each list calls through a table of its own inside the list object (the interface + 0x588 in the game's Agility SDK 618), copied from the shared direct-list table when the list is made, with the driver's functions in about 40 slots; so every list the game submits has its own table patched in the `ExecuteCommandLists` hook (each slot calling what it held: D3D12Core's function, or the driver's for RSSetViewports), and the shared table (learnt from a dummy list, hooked at install) is put back after the first list is done, so later lists copy D3D12Core's functions and are patched when submitted. Unload puts every patched table back, then scans the process's memory for pointers into the DLL and puts back any copy found in a list table. A transition out of DEPTH_WRITE (not a begin-only half, subresource 0 or all) ends a depth pass; `GetDesc` on every one (a freed resource's address may come back with another shape). The main depth: usable (2D, one sample, one slice, a 32- or 16-bit depth plane), the back buffer's aspect within 3 %, at least a quarter of its width, seen in the last 120 presents, the largest. Right after the game's first barrier on it in a present window (one copy a frame: the G-buffer's pass end; later ones counted, not copied), in the same direct list, on the game's thread, through the original function: depth subresource 0 from the state the game just set to COPY_SOURCE (skipped when that state already includes it) and our copy PIXEL_SHADER_RESOURCE to COPY_DEST, `CopyTextureRegion`, both back. Our copies: a ring of 4 (R32_FLOAT, or R16_UNORM), made at Present on the game's device when the main depth's shape changes, the old ring kept 3 s. `ExecuteCommandLists` (hooked already) marks the newest copy submitted; Present uses it when it was recorded within the last two presents. The texel: the back buffer pixel scaled by the frame's render viewport, recorded with the copy (dynamic resolution): the largest viewport set while a depth target is bound (`OMSetRenderTargets`, `RSSetViewports`; `Reset` clears a thread's state) that fits the main depth's size and aspect, in the copy's present window or the one before; else the whole depth. The scale: the game's projection (reversed, near 0.06 m, far term 0.000005: read from its memory with `probe-projection`; `draw depth near M` overrides). The deck check: three depth texels of the deck (its centre and 12 cm either way along it), through the frame's viewport and through the whole depth, are copied to a read-back buffer each frame with their view depth; (d + 0.000005) x z should give 0.06 m: the median and the middle half's spread of the last 300 show whether the texels are right, and the whole depth is used instead only when it alone agrees. The pixel shader hides a bar pixel when the scene's view depth, y / (d - x), is positive and more than `depth_bias` nearer than the bar's own (the clip-space w).
- **What it reads from the game every frame** (`src/scene.rs`; addresses from ReSkate's build tables for 20260929, every pointer checked against its class's vtable): the camera through the view manager (exe+0x75cbc48 -> views -> the local view's active camera; world matrix rows at +0x50, vertical FOV in degrees at +0xac; the game camera or the free camera); the board through the client context (a game thread's TLS world whose type is 0xbf0f9789) -> local player manager -> local player -> skater entity -> skater animation component -> board component -> board entity, whose world transform sits in its component collection at `0x10 + (first + 2 * extra) * 0x20`. Both change once a simulation tick (measured 2026-10-21: 60 Hz each, never together), so they now place the bars only as the fall-back (`bars set timing tick`); the frame's transforms (above) are the default. They still give the field of view, and the reference the proxies are found and checked against.
- **Next looks** (same pipeline, more vertex shapes): speed lines along the velocity while `speed` is high, marks under the wheels at a landing (the four wheel positions: the board's skeleton, `read_native_pose_layout` in ReSkate), smoke puffs while powersliding; effects as data (JSON, like the rules). The depth test serves them all (sprites hidden behind walls and the skater). The deck's spin needs nothing more: the board entity's transform (and its proxy) turns with the deck in flip tricks (Trevor, 13:11).
- **Video on a deck** (decided: through the DLL): the same device reaches the deck's texture (from the bound SRV when the deck draws, or by the chunk GUID Caveman wrote); each decoded frame goes into its first mip with `CopyTextureRegion` on our command list in Present (frames BC7-encoded ahead of time, or an uncompressed texture swapped in for the deck's).
- **Safety**: drawing installs only when asked (`draw test on`, `bars on`) and only in the verified build (or a test host); nothing blocks a frame for more than 2 ms; failures skip the frame and 300 in a row turn drawing off; panics are caught; none of the game's D3D objects is released by us beyond the references we took; unload puts every slot back (refused, staying loaded, when another hook sits on ours), waits for threads in our hooks, 0.3 s more when depth copies were recorded into the game's lists (lists recorded before the unhook may not have run), and for our GPU work, and releases everything. If the D3D12 work fails, the getter hook and the rules run on as before.

- The art goes up but the deck still shows white: the deck draws another texture (a cached preview?): `board probe` again, compare the resource with the one written (`board status --json`, `last_upload.resources`).
- `draw depth off` stops the barrier watch (the board then trusts what it saw so far and the inference): keep it on while testing the board.

## Pin anything: the DLL's drawing roadmap (Trevor, 2026-10-21)

The DLL reads the game's real transforms (camera, board, soon the per-pixel depth), so anything it draws is pinned exactly, with no tracking or drift. **Trevor wants stylized looks** (neon, flat colour, outlines, comic effects): they suit drawing on the finished frame, where our art gets no game lighting, shadows or motion blur. Roadmap, after depth occlusion works:

- **Skeleton pins**: the skater's bones (head, hands, feet) as the board is found now (render proxies of skinned meshes): foot trails, halos, fire hands; other skaters too.
- **Surface decals from depth**: reconstruct the world position (and a normal from depth derivatives) under any pixel and draw images onto surfaces: powerslide skid marks, landing scorches or craters, a tag on the wall being grinded past, footprints.
- **Silhouette effects**: the skater's shape from depth: a glowing outline, comic ink edges.
- **Bars that cling to the real deck edge** (Trevor, 2026-10-21; **built that evening**, the `rim` layout, see Status; in game: pending): the ring is flat at the bars' height, but the deck's nose and tail kick up. Computed at run time from the install: no game geometry shipped. No rim sent: the ring.
